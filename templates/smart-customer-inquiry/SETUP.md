# Setup

## Quick start requirements

- n8n **2.45.0 or later**. The earlier workflow was manually imported by the operator on self-hosted n8n 2.46.7; this v1.1.2 patch still requires the isolated runtime acceptance test in [TESTING.md](TESTING.md).
- The built-in Form Trigger, Data Table, Schedule Trigger, Code, Switch, If, and Send Email nodes, plus one SMTP credential.
- A test Data Table and test-only internal recipient mailbox. Slack is optional and remains disabled.

## Mandatory setup

1. In a non-production n8n project, import `workflow.json` from **Workflows → Import from File**. Keep it inactive. If you imported an earlier copy of this template, import this corrected file as a new workflow; n8n does not automatically update imported workflows.
2. Open **Data Tables** in the same project and create a table named `customer_inquiries`. Add every column shown below with the stated type. Copy its ID from the table URL/UI.
3. In all 10 Data Table nodes, replace `REPLACE_WITH_DATA_TABLE_ID` with that table ID. Keep the column names exact so automatic mapping works.
4. Open **Normalize, validate & classify (CONFIG HERE)** and update the plain `cfg` values. Set the workflow timezone in workflow settings. The timezone governs the schedule display/execution, but the reminder intervals remain elapsed hours rather than business hours.
5. Create an SMTP credential in n8n. Select it in all three Send Email nodes: **Send internal new-inquiry alert**, **Send internal follow-up reminder**, and **Retry internal new-inquiry alert**. Replace the example sender, internal recipient, and escalation recipient addresses. If the escalation recipient should be the same team, deliberately set both placeholders to the same internal address. Do not use the submitted customer's address as an internal recipient. The reminder node's one recipient expression deliberately selects the ordinary or escalation recipient.
6. In **Customer inquiry form**, replace `REPLACE_WITH_YOUR_PRIVACY_NOTICE_URL` in the Form Description with the hostname/path portion of your public privacy-notice URL (the template already includes `https://`), then open the test form and verify the information/link and acknowledgement wording. Do not publish while the placeholder remains. This acknowledgement is for handling the inquiry, not marketing consent.
7. To start an intake test, select **Customer inquiry form** and click **Execute step** (or **Execute workflow**). Submit the Test URL opened by n8n. This is the upper branch. The lower scheduled branch cannot be started from the form; execute **Scheduled inquiry check (every 15 min)** only after a test row exists.
8. In **Data Tables**, change a row status to `Acknowledged`, `In progress`, `Waiting for customer`, `Resolved`, or `Closed`. Update `last_activity_at` when a person acts. Do not reopen Closed records.
9. For a reminder test, set an open test row's `next_reminder_due_at` in the past, `reminder_count` below `3`, and `status` to `New`, then manually execute from **Scheduled inquiry check (every 15 min)**. Inspect **Explain reminder eligibility** before checking the email and updated next due date.
10. Publish the workflow and use the Form Trigger's production URL only after the preceding checks pass. Schedule triggers require publishing.

## Optional Slack alerts

Slack is deliberately disabled and does not block the default SMTP workflow.

1. Create a test Slack credential with permission to send messages to a test channel.
2. Select **Optional Slack alert — enable after setup**, attach the credential, and replace `REPLACE_WITH_SLACK_CHANNEL_ID`.
3. Enable that node, then change the boolean expression in **Slack enabled for High/Critical?** from `false` to `true`.
4. Submit a High or Critical synthetic inquiry and verify the Slack message contains only the ID, priority, category, subject, submission time, and owner.
5. Test a failed Slack credential in the isolated environment. Leave Slack disabled if it is not wanted.

## Table schema

### Upgrade from v1.1.1

Do not delete or recreate the table. Add the five `initial_notification_*` columns below with their stated types, then import v1.1.2 as a new inactive workflow and test with synthetic data. Existing rows without these values aren't eligible for initial-alert retries; they retain their existing reminder behavior.

| Column | Data Table type | Purpose |
| --- | --- | --- |
| `inquiry_id` | String | Human-readable unique best-effort identifier. |
| `full_name`, `email`, `phone`, `company` | String | Contact fields; keep access restricted. |
| `category`, `subject`, `message`, `preferred_contact_method` | String | Inquiry content and stated preference. |
| `consent` | Boolean | Privacy acknowledgement received with the submission. |
| `priority`, `status`, `assigned_owner`, `source` | String | Operational routing and lifecycle. |
| `submitted_at`, `last_activity_at` | Date | Required ISO-8601 timestamps generated by the workflow. |
| `last_reminder_at`, `last_duplicate_at`, `last_retry_at`, `resolution_at`, `initial_notification_last_attempt_at` | Date | Optional timestamps. Leave cells empty in the UI; the workflow sends `null` until a value exists. |
| `follow_up_due_at`, `next_reminder_due_at`, `initial_notification_next_retry_at` | Date | Initial/next reminder due timestamps and the pending initial-alert retry time. The scheduler uses all due fields independently. |
| `reminder_count`, `reminder_stage`, `notification_attempts`, `reminder_retry_count`, `initial_notification_attempts` | Number | Successful reminder stages, legacy initial notification count, failed reminder delivery attempts, and total initial-alert attempts. Initial attempts include the original send. |
| `notification_state`, `last_notification_outcome`, `processing_state`, `error_state`, `escalation_state`, `delivery_failure_state`, `last_retry_error`, `initial_notification_state`, `initial_notification_last_error` | String | Processing/audit state. Initial states: `pending`, `retry_pending`, `provider_accepted`, `initial_notification_failed`. `provider_accepted` means SMTP accepted the request, not inbox delivery. |
| `duplicate_of`, `dedupe_key` | String | Duplicate handling; treat dedupe key as personal data. |

Do **not** add `duplicate_window_start` to the Data Table. It is a temporary query helper, removed by **Remove temporary duplicate-window value** before a record is stored.

## Optional hardening

- Put the public form behind your site, reverse proxy, CAPTCHA/WAF, rate limit, and privacy notice. **Ignore Bots** is enabled but is not an abuse-prevention system.
- Use a dedicated least-privilege SMTP account. Restrict project membership because Data Tables are project-visible.
- Set a data-retention/deletion procedure. Export then securely delete old rows after the required retention period.
- Add a separate Error Trigger workflow to notify an operator using an internal, non-PII execution reference. Do not make it call this workflow recursively.

## Recovery

Storage errors stop the relevant execution before an alert is sent. SMTP nodes use continue-on-fail so the saved row is retained. Initial-alert failure 1–2 becomes `retry_pending` and is retried after 15 minutes; failure 3 becomes `initial_notification_failed` and stops automatic initial-alert retries. To resume it safely, correct SMTP, set `initial_notification_state` to `retry_pending`, keep `initial_notification_attempts` at `0`, clear `initial_notification_last_error`, and set `initial_notification_next_retry_at` to a controlled test time. This never creates a new inquiry or changes reminder stage/count. Reminder delivery failure 1–2 becomes `retry_pending` and is retried after 60 minutes without changing `reminder_stage` or `reminder_count`; failure 3 becomes `delivery_failed`. Inspect **Executions** and current durable state before any retry.
